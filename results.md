## Findings

1. **T12, platform fleet grant.** The platform binds `roles/aiplatform.agentDefaultAccess` (includes `aiplatform.endpoints.predict`) to the project-wide agent principalSet when the first agent is deployed. Our Terraform grants none.
2. **Quota project outside the perimeter is evaluated as egress.** With the perimeter enforced, Terraform and gcloud calls that send the seed project as quota project were refused as `RESOURCES_NOT_IN_SAME_SERVICE_PERIMETER`; billing the project inside the perimeter avoided it.
3. **Enforced-mode VPC-SC log entries have no `dryRun` field.** A filter `dryRun!=true` does not match them.
4. **Cloud Storage CMEK refusals do not name the constraint** in the error or the audit log (T07, T10).
5. **Cloud Build default staging bucket is created in `us`**, so `gcp.resourceLocations` blocks a plain `gcloud builds submit` before CMEK is evaluated (T10).
6. **Model not served in europe-west1.** The agent runtime sent model calls to the agent region (europe-west1) where `gemini-3.5-flash` was not found; the fixture was changed to call the `global` endpoint (T14). Global processing may be outside the EU.
7. **Agent deployed before the project joins a perimeter is refused as an outside caller after enforcement (T14R).** Its own Vertex AI call was refused with `NO_MATCHING_ACCESS_LEVEL`; the agent stopped working. Internet egress could not be observed.
8. T06: the effective setting was already enforced by Google default.
9. **T22, one quota project cannot serve a stack that spans the perimeter (v1.1, run-4).** With the perimeter enforced, a tooling quota project inside the perimeter removes F5 for in-perimeter resources. The lookup of the project outside the perimeter, billed to that quota project, is refused (403 `SECURITY_POLICY_VIOLATED`, `vpcServiceControlsUniqueIdentifier`): the mirror of F5. A Terraform stack that manages projects on both sides of the perimeter boundary cannot use one quota project. Run 4 recorded T22 INCONCLUSIVE because the script did not recognise this 403 text. Run 5 saw the same single plan error ("Request is prohibited by organization's policy. vpcServiceControlsUniqueIdentifier"); after a second script fix (the check had read the wrong output) the stage was recorded FAIL in run-5-r2. The expected result was not changed. Two runs, same behaviour.
10. **Observation, not a test result: the mcp project's Compute Engine default service account holds `roles/editor`.** Seen during T21 and T25 work (Google's automatic grant to default service accounts; the builds ran as this account). The test folder has no `iam.automaticIamGrantsForDefaultServiceAccounts` policy. No test covers it ([run-4.md](evidence/runs/run-4.md), stage 3 observation).
11. **T19, the platform adds one binding at agent deploy.** Deploying one agent added exactly one binding, `roles/aiplatform.agentDefaultAccess` on the runtime project's agent principalSet. No other binding was added or removed at the three projects and two folders. This repeats the v1 T12 grant (F1) as an observed diff (run 4). In run 5 the binding was already present before the deploy: it stayed on the project after the run-4 agents were deleted, so the deploy added no binding at all. Run 5 therefore does not repeat "added at deploy"; it shows that the deploy added nothing else, and that the binding is not removed when the project's agents are deleted.
12. **T18, the deny text names the IAM deny policy.** The refusal of the non-approved agent read "Permission 'aiplatform.endpoints.predict' denied ... due to an IAM deny policy", not a generic text as the doc check expected. The pre-registered signature (`PERMISSION_DENIED`) was met. Creating a deny policy needed `roles/iam.denyAdmin`, which Security Admin does not include.
13. **T21, a CMEK build bucket in another project needs `roles/storage.admin` for the build service account.** Object-level roles were not enough (attempts r1 and r2 failed on bucket access). Cloud Build ran as the compute default service account because the compute API was enabled in the build project.
