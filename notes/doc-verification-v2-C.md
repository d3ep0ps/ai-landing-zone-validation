## 3. ADK agent to SWP over PSC-I
- Mechanism (codelab): proxy value in env (`.env`: `PROXY_SERVER_URL=http://swp.demo.com:8888`); agent code `os.environ["PROXY_SERVER_URL"]` passed to `requests` as `proxies` for http and https. It is application-level, not automatic. Our equivalent: `agent_runtime_config.environment_variables` (maps to `deployment_spec.env`) plus a fetch tool that passes `proxies=`. The existing probe agent's fetch tool must be extended (new tool arg or env switch); `HTTPS_PROXY` env alone works for `requests`/`urllib` but is not documented for Agent Runtime, so use explicit `proxies=`.
- Reaching the gateway: codelab SWP is `type: SECURE_WEB_GATEWAY`, `ports: [8888]`, `addresses: ["10.10.10.5"]`, `subnetwork: swp-subnet (10.10.10.0/28)` which is a DIFFERENT subnet from the attachment subnet (192.168.10.0/28); `routingMode: EXPLICIT_ROUTING_MODE`. So the gateway is reached by routing from the attachment subnet inside the VPC; no need to put it in the attachment subnet. The page says the interface "can route to VPC or on-premises destinations learned by the VPC network".
- Firewall (codelab): `allow-access-to-swp` EGRESS ALLOW priority 1000, source-ranges 192.168.10.0/28, destination 10.10.10.5/32, logging; `deny-all` EGRESS DENY priority 65534, 0.0.0.0/0, logging. Firewall log shows `"disposition": "ALLOWED"` and `"src_ip": "192.168.10.2"` (attachment subnet), which shows the VPC firewall evaluates agent traffic by attachment-subnet source. No blocked example in the codelab. Ingress to the gateway from the attachment subnet: not in the codelab (VPC default allows are not present in a custom VPC); infra/v11-swp.tf already adds an ingress allow for the job subnet, add the attachment subnet.
- Other quotes: "You must provide internet egress connectivity within the customer VPC for the Agent Engine PSC-Interface to function"; "If TLS inspection is not enabled, application matcher request.method == 'GET' will only match HTTP traffic".
- Decides: T33 reuses the v1.1 gateway (10.77.0.10:443, host matcher `example.com`), so the proxy URL is `http://10.77.0.10:443`.
- UNVERIFIED: whether a gateway on port 443 without TLS inspection serves `CONNECT` to a client speaking plain HTTP proxy protocol (T16 certificate section still medium; v1.1 T16 evidence should show it).

## 4. PSC-I plus enforced perimeter; PSC-I without perimeter
- With perimeter: "When your project is part of a VPC Service Controls perimeter, the agent's default internet access is blocked by the perimeter to prevent data exfiltration." and "PSC interface is required to enable internet access when using VPC Service Controls" (Vertex PSC/VPC-SC and Agent Runtime pages). Limitation: "When using VPC Service Controls with Agent Runtime, the project must be part of a service perimeter before you deploy the agent." and "If an agent is deployed before the project is added to a perimeter, the agent won't be secured by VPC Service Controls and continues to have access to the public internet."
- Without perimeter, with PSC-I: Runtime page: "By default, your VPC doesn't provide an outbound path to the public internet for this traffic." The Vertex VPC-SC page, PSC section: "The exception to this behavior is Agent Runtime, which doesn't provide internet egress." Older text said the agent retains default internet access when configured with only a PSC interface. Docs are not consistent over time; the current wording says PSC-I removes the default path (traffic goes through your VPC, which only has the proxy path plus whatever NAT/routes you add). This is a documented expectation, not observed.
- Decides: T34 expected result "bypass fails" is supported by docs in both perimeter and no-perimeter cases, but the cause cannot be attributed to the firewall by the failure alone (no NAT/route also fails). Attribute by the firewall log deny entry from the attachment subnet (see proposals). T35 is not needed to decide T34.
- Open: exact exception text from the agent (undocumented).

## 5. Perimeter alone (no PSC-I)
- Docs (quotes above): "default internet access is blocked by the perimeter" for a project in a perimeter, with the deploy-after-join ordering rule. Pages do not say whether this applies to agents without a PSC interface; the statement "PSC interface is required to enable internet access when using VPC Service Controls" implies it does.
- Observed in this repo (PROGRESS.md, not from docs): T23 pre: agent A deployed outside any perimeter fetched example.com: 200. v1.1 T23 post/ agent B deployed after enforcement: "Network is unreachable". So both halves of T35 were already observed in v1.1 for a no-PSC-I agent (trap #7 at least for the pre-perimeter 200). T35 as drafted would repeat T23; propose to drop or reduce it (see below).
- Decides: T35 is a duplicate of T23 unless it also covers "agent deployed before join keeps internet access after enforcement" (the documented ordering limitation). That variant was not observed (T14R post was INCONCLUSIVE due to ingress denial of the agent's own CreateSession; with C16 agent ingress this may now be observable).
