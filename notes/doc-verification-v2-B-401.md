# v2 area B: 401 UNAUTHENTICATED behind Agent Gateway (doc verification)

Accessed 2026-10-28, docs only; no cloud state touched. Status marks: VERIFIED (doc states it), INFERRED, NOT FOUND.
Short summary: our reading is SUPPORTED by Google docs, and the documented/observed workaround is to opt out of the default Context-Aware Access (CAA) token binding with env var GOOGLE_API_PREVENT_AGENT_TOKEN_SHARING_FOR_GCP_SERVICES=False in the agent's env_vars. The docs' own gateway deploy samples set it.

## 1. Certificate-bound tokens; can binding be turned off? (VERIFIED)
- Agent Identity tokens are certificate-bound by default. Quotes:
  - agent-identity-overview: "This token is cryptographically bound to the agent's unique X.509 certificate to help prevent token theft."; default Google-managed CAA policy "enforcing mTLS and DPoP token binding".
  - runtime-setup troubleshooting (401 section): "Agent Runtime uses certificate-bound access tokens by default"; symptoms "Context-Aware Access requirements are not met" / "Request had invalid authentication credentials".
- Gateway interaction (VERIFIED, caa-agent-security): "When Agent Gateway is disabled, agents can directly access Google Cloud APIs through mTLS." "When Agent Gateway is enabled, however, the gateway terminates mTLS, so DPoP must be used." "because mTLS terminates at the Agent Gateway, DPoP must be used to reauthenticate the agent." DPoP is "based on RFC 9449"; resource proof is "A cryptographic proof that's generated by Agent Gateway and provided to Google Cloud APIs." Our "TLS re-origination breaks the binding" is therefore the documented design problem, but the docs say DPoP is the fix path; whether it works end to end for the Vertex session call is not documented (see 3, 5).
- Turning binding off (VERIFIED): runtime/agent-identity#opt-out-caa: "you can opt out of the default CAA policy" ("strongly discouraged, as it leaves an agent vulnerable to credential theft"); set env var `GOOGLE_API_PREVENT_AGENT_TOKEN_SHARING_FOR_GCP_SERVICES` to `False` "when you create the Agent Runtime instance" (runtime-setup: in the `env_vars` config).
- No other non-bound token type for agents found (NOT FOUND). Agent-identity-overview lists "X.509 certificates, Google Cloud access tokens, and OIDC ID tokens" without a gateway-specific choice.
- URLs: https://docs.cloud.google.com/iam/docs/agent-identity-overview ; https://docs.cloud.google.com/access-context-manager/docs/caa-agent-security ; https://docs.cloud.google.com/gemini-enterprise-agent-platform/troubleshooting/runtime-setup ; https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/agent-identity

## 2. Support matrix: Agent Identity behind the gateway; modes (VERIFIED, partial)
- Supported: runtime-deploy page: "Deployments that specify agent_gateway_config must set identity_type = 'AGENT_IDENTITY'." and "The backend enforces identity_type = "AGENT_IDENTITY" at the API level whenever agent_gateway_config is specified". So Agent Identity behind the gateway is the only documented combination; service-account agents behind the gateway are NOT FOUND (the API forces AGENT_IDENTITY).
- Agent-identity-overview: "The following services support Agent Identity": Agent Runtime, Gemini Enterprise, Cloud Run.
- Modes: gateway modes are ingress (Client-to-Agent) and egress (Agent-to-Anywhere); "Agent Gateway supports only Agent-to-Anywhere (egress) mode" for Gemini Enterprise (from notes/doc-verification-v2-B.md). No page found that gives different support for Gemini Enterprise mode vs standalone for the token problem (NOT FOUND).
- Limits listed: no gateway on engines created before 2026-04-29; SCC Agent Engine Threat Detection unavailable when a gateway is enabled; changing the binding archives revisions.
- URL: https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/agent-gateway-runtime-deploy

## 3. TLS interception and upstream authentication (VERIFIED partly; mechanism NOT FOUND)
- VERIFIED: "Because Agent Gateway performs TLS decryption and inspection on outbound agent communications" (runtime-deploy); gateway offers "built-in zero-maintenance mTLS termination" (overview); trust config: "By default, Agent Gateway only trusts certificates issued by publicly trusted CAs."; for Google APIs keep `additionalRoots` = `PUBLICLY_TRUSTED_ROOTS` in `tlsConfig` (troubleshoot-agent-gateway). Agent-side: BYOC images must trust the gateway CA (`agentGatewayCard.rootCertificates`, REQUESTS_CA_BUNDLE).
- NOT FOUND: any statement on whether the gateway forwards the agent's token, swaps credentials, or how it produces DPoP for the upstream call. Overview says only that gateway "transparently handle[s] OAuth 2.0 handshakes" via Agent Identity Auth Manager (a different feature). Essential endpoint list includes mTLS hostnames ("register each standard, regional, and secure (mTLS) hostname variant").
- Observation matching our log: GitHub python-aiplatform#7209 (see 5) shows the same signature: authzPolicyInfo ALLOWED, requestWasTlsIntercepted=true, clientCertPresent=true, then 401 from aiplatform.mtls.googleapis.com.
- URLs: https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/gateways/agent-gateway-overview ; https://docs.cloud.google.com/gemini-enterprise-agent-platform/troubleshooting/troubleshoot-agent-gateway ; runtime-deploy page above.

## 4. iapPolicyVersion V2 (VERIFIED for recommendation; effect on upstream auth NOT FOUND)
- delegate-authorization: "The `iapPolicyVersion` field under `metadata` is mandatory." V1 = "legacy Allow policy"; "We strongly recommend using Unified Access Policy" (V2). Release note 2026-08-31: IAM Unified Access Policies GA.
- NOT FOUND: any statement that V2 changes upstream authentication or token handling. V2 only governs authorisation (IAP egress). Since our log shows IAP ALLOWED and the failure is upstream (Google API), INFERRED: V2 will not fix the 401. Also #7209 reporter's failure/success flip is the token-binding variable only.
- URL: https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/gateways/delegate-authorization ; https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes

## 5. Known issues, release notes, regions (VERIFIED: known issue; region NOT FOUND)
- Official troubleshooting (runtime-setup) lists the 401 "Request had invalid authentication credentials" with CAA / certificate-bound tokens, but does not mention the gateway. troubleshoot-agent-gateway has no 401/DPoP entry. Release notes: only the 2026-08-31 entry mentions "Context-Aware Access (CAA) with Demonstrating Proof of Possession (DPoP)"; no 401 entry.
- Public report of our exact case, open, no Google reply as of access: https://github.com/googleapis/python-aiplatform/issues/7209 (opened 2026-10-12, us-central1, Agent Runtime + AGENT_IDENTITY + Agent-to-Anywhere gateway): 401 UNAUTHENTICATED from `aiplatform.mtls.googleapis.com` with authz ALLOWED, requestWasTlsIntercepted=true, clientCertPresent=true. "Token binding enabled: reproducible 401; disabled: reproducible success" with `GOOGLE_API_PREVENT_AGENT_TOKEN_SHARING_FOR_GCP_SERVICES=False`; after that, Gemini call and MCP tools/call through the gateway succeed (gateway log tools/call ALLOWED, IAP audit egressViaIAP granted). Issue Tracker 572540590 per forum https://discuss.google.dev/t/agent-runtime-agent-to-anywhere-gateway-401-with-runtime-bound-agent-identity-token-succeeds-when-token-binding-is-disabled/403493 (third-party reports, not Google statements).
- Official sample: runtime-deploy page, both Python SDK examples (Agent-to-Anywhere and Client-to-Agent) set `"env_vars": {"GOOGLE_API_PREVENT_AGENT_TOKEN_SHARING_FOR_GCP_SERVICES": False}` with a comment linking `agent-identity#opt-out-caa`. The page does not explain it. Terraform examples on that page have no env_vars (VERIFIED by absence).
- Related closed: https://github.com/google/adk-python/issues/6365 (A2A 401 with Agent Identity, fixed by ADK PR #6370, closed 2026-07-28; ADK mTLS-endpoint handling). Our ADK version should be checked against that fix (INFERRED relevance).
- europe-west1: no feature limit or region list found (NOT FOUND). Our own run-6 shows gateway create works there. #7209 is in us-central1, so the 401 is not region specific (INFERRED).
