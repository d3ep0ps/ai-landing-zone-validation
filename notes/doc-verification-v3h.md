## T47/T48 (B8/B9): env var semantics, enforcement, endpoint, error
- NEW FINDING, variable renamed (VERIFIED by source, google-auth 2.62.1 `environment_vars.py` and `_agent_identity_utils.py`): `GOOGLE_API_ENABLE_RUNTIME_BOUND_TOKEN` exists; "Defaults to enabled; only a case-insensitive "false" disables it. When set to a non-empty value, this variable takes precedence over `GOOGLE_API_PREVENT_AGENT_TOKEN_SHARING_FOR_GCP_SERVICES`", which is marked ".. deprecated:: v2.59.0 Use GOOGLE_API_ENABLE_RUNTIME_BOUND_TOKEN instead." The deprecated var still works as fallback (default "true"; opt-out only when its value lower-cases to "false"). The web docs (agent-identity, caa-agent-security, runtime-setup troubleshooting) mention only the old name; the new name has no doc page (web search found none). Consequence: with google-auth >= 2.59.0 set only the old var (as the docs do) and keep the new one UNSET; a stray non-empty `GOOGLE_API_ENABLE_RUNTIME_BOUND_TOKEN=true` would override an old-var opt-out and keep binding on. google-cloud-aiplatform 2.6.0 requires `google-auth>=2.47.0`, so the resolved version could be below 2.59.0 unless pinned; pin google-auth >= 2.59.0 (or record the resolved version in each run). `requirements.txt` currently has unpinned `google-auth`.
- Exact semantics (VERIFIED by source): the switch is CLIENT-SIDE. When opted out, `get_agent_identity_certificate_and_bytes()` returns `(None, None)` and `should_request_bound_token()` returns False, so the library does not send `bindCertFingerprint` to STS (or asks the metadata server for an unbound token); it also skips the cert lookup. When not opted out, the token is requested bound to the agent certificate's SHA-256 fingerprint (base64, unpadded, URL-encoded), only if the cert is an agent identity certificate and `GOOGLE_API_USE_CLIENT_CERTIFICATE` does not disable client certs. Docs wording: set it "when you create the Agent Runtime instance" (env_vars); docs say opting out "leaves an agent vulnerable to credential theft". Whether the platform itself also changes server-side CAA behaviour for the instance is NOT FOUND.
- Enforcement by Vertex AI (PARTLY VERIFIED): docs say the default policy is "a Google-managed Context-Aware Access (CAA) policy" enforcing mTLS binding, credentials "can only be used from their intended, trusted runtime environment", and using a token outside the intended runtime returns "Error Code: 401, Error Details: Context-Aware Access requirements are not met" (agent-identity page and runtime-setup troubleshooting). NOT FOUND: a per-service list; the docs do not say that `aiplatform.googleapis.com` is enforced. Evidence that it is: #7209 (and our run 6) shows 401 from `aiplatform.mtls.googleapis.com` for a bound token via the gateway, and `telemetry.googleapis.com` is the documented example that fails on the non-mTLS endpoint.
- Which endpoint (VERIFIED, runtime-setup troubleshooting): scenario 2 "An agent calls a non-mTLS endpoint, such as telemetry.googleapis.com" returns the same 401; fix is `telemetry.mtls.googleapis.com` (or the opt-out as "a temporary workaround"). So a bound token needs the mTLS endpoint plus the matching client certificate; with the regular endpoint it is refused even from the legitimate agent. INFERRED for Vertex: `aiplatform.mtls.googleapis.com` and the regional `LOCATION-aiplatform.mtls.googleapis.com` (regional variant not verified).
- Expected error when a bound token is replayed elsewhere (VERIFIED text, two doc pages): HTTP 401, details "Context-Aware Access requirements are not met"; the troubleshooting page also lists the generic "Request had invalid authentication credentials. Expected OAuth 2 access token, login cookie or other valid authentication credential." (status UNAUTHENTICATED). The exact JSON body for aiplatform is not documented; capture and record it.
- T48 design caveats: (1) a replay from another workload over the regular endpoint conflates two causes (no client cert vs. wrong cert); both give the same 401. To attribute it to binding, add a control: the same token from the agent itself over the regular (non-mTLS) endpoint, and over the mTLS endpoint with its own cert (expected 200). Replaying over mTLS from the other workload requires a client certificate that is not the agent's; a Cloud Run job has none (it would be non-mTLS). (2) Capture the token in-process: with the opt-out, the token is simply unbound (no fingerprint at STS), so replay success is by construction a client-side choice; the interesting claim is the bound case being refused. (3) 403 vs 401 ordering: CAA is evaluated before IAM per the T48 text; not documented, so a 403 must be recorded as a finding.

- Confidence: high (client semantics, 401 text, endpoint rule); medium (Vertex enforcement); low (exact aiplatform body).
