# Limitations

What was not tested, what was inconclusive, and what a single small test organization cannot show. Verdicts and corrections follow [results.md](results.md) and [errata](evidence/runs/errata.md).

## Caveats that apply to every result

- **Single small test organization.** One organization, four projects, one operator. Nothing here was tried in a second organization or with different existing policies.
- **Folder-scope policies.** The constraints under test were applied to the test folders (`fldr-lz-validation`; `vertexai.allowedModels` on the AI prod folder), not at organization level. [The supplement](evidence/supplement/policy-sources-2026-10-25.txt) (collected 2026-10-25 after the runs, at base state, read-only) shows where policies are set: the only organization-level policy is `iam.allowedPolicyMemberDomains`; no project-level policies; the constraints under test exist only on the test folders (the T05/T06/T07 toggle policies had been removed by then). Behavior with policies set at organization or project level, or with inherited exceptions, was not tested.
- **Region.** Resources and locations were europe-west1 and EU. Agent model calls used the `global` endpoint (model not served in europe-west1). Other regions and multi-region behavior were not tested.
- **Dates.** Run 1: 2026-10-23..24. Run 2: 2026-10-25. Run 3 (T14R): 2026-10-25. Runs 4 and 5 (v1.1): 2026-10-25..27. Run 6 (v1, v1.1 and v2 tests in one order): 2026-10-27..28. Run 7 (the same, second v2 run): 2026-10-28..29. Run 8 (area B only): 2026-10-30. Run 9 (area B repeat plus T31R): 2026-10-30. Google Cloud behavior, preview features and constraint names can change after these dates.
- **Fabric commit.** Terraform modules were taken from the Cloud Foundation Fabric checkout at `be0d4b10e4f8c6969d2f7a4faee086504b334fd0` (2026-10-22). Tool versions recorded in every `result.json`: gcloud 583.0.0, Terraform 1.17.0, Google provider 8.8.0 (`notes/tool-versions.txt` lists Terraform 1.16.6 from Phase 0, before an upgrade).
- **Evidence collected after a run is labeled.** The supplement above and `evidence/T14R/run-3/post-audit-lookup.txt` were read after the results were recorded. They explain a result; they do not change it.
- **Runs.** Run 2 used the scripts as fixed during run 1, so it is a repeat of the corrected scripts, not an independent design. Some run-2 tests ran in parallel.
- **Runtime project replaced.** Google suspended the first runtime project during run 1 (reason not stated beyond a Terms of Service notice). T01, T04, T05 were repeated in the replacement; T11, T12, T14 ran only there.
- **Attempts as one operator.** Denials were produced by an operator account and a test service account, not by a range of caller identities.

## v1.1 limitations

- **Two runs, same environment.** v1.1 tests ran in run-4 (2026-10-25; T16 on 2026-10-26) and run-5 (2026-10-26..27). Run 5 repeats the expected results of run 4, but not its order: it used two agent deploys instead of four, ran T18 with the perimeter enforced, and ran with script and fixture fixes made during run 4. Both runs used one organization, the same projects and one operator, so they show repeatability there only. Each run is listed separately in results.md; the results are not pooled.
- **T16 scope.** Cloud Run jobs with Direct VPC egress only; Agent Runtime through a PSC interface was not tested. One allowed host (`example.com`), one non-allowed host, one gateway in explicit proxy mode, one region. In both runs the job subnet and VPC could not be destroyed at once because Cloud Run still held a serverless IP address in the subnet. The run-4 subnet and VPC were kept and reused by run 5; after run 5 they are still waiting for deletion (free resources).
- **Second runtime project suspension, 2026-10-25/26.** The replacement runtime project was suspended as an API consumer (`CONSUMER_SUSPENDED`). The suspension notice is not part of the evidence, and no reason is recorded. The operator submitted an appeal, and Google reinstated the project on 2026-10-26 without giving a reason. The last successful runtime call before the suspension was T23 `post` (2026-10-25). The suspension delayed T16 by a day. The cause is not known and is not claimed.
- **T22 verdicts and script faults.** Run 4 recorded INCONCLUSIVE: the script's error signature did not match the 403 text. The signature was widened before run 5, but run 5 still recorded INCONCLUSIVE, because the check read the output of the gcloud call that ran after the plan (shared output file). That fault was fixed (023ce5a) and the enforced stage re-run as run-5-r2, which recorded FAIL. The run-5-r2 dry-run stage is a copy of the run-5 record, not a new measurement. The expected result was never changed. The perimeter-spanning limitation (Findings 9) rests on one plan error per run, in two runs, both on the same resource (the GCS service account lookup of the outside project).
- **T22 evidence.** The first dry-run record (`evidence/T22/run-4`) has stage records only and no `result.json`. Its count was a measurement fault (ingress entries counted); the passing dry-run stage is in `run-4-r2`.
- **T21 took three attempts.** The first two were INCONCLUSIVE because of fixture gaps in bucket access for the build service account. The final PASS is run-4-r3, after the fix. The build ran as the compute default service account, which holds `roles/editor` (Findings 10).
- **T20 attribution.** By elimination; no audit entry named the constraint.
- **T19 tier.** Configured: allow-policy snapshots before and after one agent deploy. Deny policies were not part of the diff and none existed.
- **T19 run 5 does not repeat the run-4 observation.** The `roles/aiplatform.agentDefaultAccess` binding was already present before the run-5 deploy (it stayed after the run-4 agents were deleted), so run 5 saw no binding added. The human granted `roles/iam.denyAdmin` to themselves at organization level to create the policy. Decision 2026-10-28: that grant is kept for run-7, not removed at teardown.

- **T24 scope.** One admin action, one folder sink. The locked bucket is in the data project, not a dedicated logging project (deviation from DC4 as designed, because of a billing limit on linked projects). The bucket cannot be deleted.

- **Fixture and script changes during run 4.** T19 guard, T18 parser, T21 grants, T22 matcher and quota-project passing, T25 cleanup. None changed an expected result. Details in [run-4.md](evidence/runs/run-4.md).

## v2 limitations (runs 6, 7 and 8)

- **Two runs, one environment.** The v2 tests (T27 to T39) ran in run 6 (2026-10-27..28) and run 7 (2026-10-28..29), with the same verdicts, on the same environment and by the same operator (`EXECUTION-PLAN.md` E5 item 4). This shows repeatability there, not in other organizations. Area B used a different setup in runs 6, 7 and 8; runs 8 and 9 used the same setup (T30, T32 PASS in both).
- **Area B is not shown in run 6.** T30, T31 and T32 are all INCONCLUSIVE. The gateway authorised the agent's calls (IAP extension V1 and Model Armor policy ALLOWED, registry match) and intercepted TLS, and Vertex AI returned 401 `UNAUTHENTICATED` to the forwarded session call. This persisted after registering the essential endpoints and redeploying agent G in the documented order (three attempts for T30). No claim is made about gateway tool authorisation, model-path blocking or Model Armor on tool responses. Not tested in run 6: `iapPolicyVersion` V2 (we used V1), regions other than europe-west1, Gemini Enterprise mode. T31 part 2 (non-approved agent refused by the deny policy) was not run. The cause of the 401 is a reading, not verified.
- **Area B in run 7 (changed setup) is not shown either.** Agent G opted out of certificate-bound tokens (`GOOGLE_API_PREVENT_AGENT_TOKEN_SHARING_FOR_GCP_SERVICES=False`), its packages were pinned, and IAP used policy V2. No 401 was seen and the agent queries returned 200 (some forwarded telemetry and credential calls still got 403 or 404), but the opt-out gives up a default protection, and which of the three changes removed the 401 was not isolated. The registered MCP fixture was unreachable from the gateway: Cloud Run ingress is `internal` (folder policy `run.allowedIngress`) and the gateway had no VPC egress, so the front end answered 404. Setting ingress `all` was refused by the policy. A post-run lookup of the gateway request log shows IAP V2 `DENIED` with 403 for an unregistered MCP server (no request reached it) and for a blocked model endpoint, and the allowed endpoint answered 200. The scripts' own log checks had a matcher fault and did not isolate these entries. No injected tool response passed the gateway, so Model Armor on tool responses was not exercised (the T32 `actual` text "Model Armor finding logged" is a matcher fault; all entries were `NO_MATCH_FOUND`). These are single observations, not test passes. Not tested: gateway egress through a network attachment, regions other than europe-west1, Gemini Enterprise mode. T31 part 2 was not run (stop rule).
- **Area B in run 8 (VPC egress added).** T30 and T32 passed once, in one run, with a setup that differs from the default in three ways: the agent opts out of certificate-bound tokens (the default setup failed with 401 in run 6), IAP policy V2, and gateway egress through a network attachment with a private `run.app` zone. One registered and one unregistered MCP tool; one injection sample and one Model Armor template; europe-west1; one project. The T32 block reached the agent as HTTP 403, not the terminated connection the expected text names (the script does not assert the form). T30's container-log check read the log too early; the container request is shown by a post-run lookup. The gateway request log does not record every request (successful MCP calls and two of three blocked-model calls had no entry), so tests that rely on it can come out INCONCLUSIVE, as T31 did. Not tested: Gemini Enterprise mode, other regions, VPC Service Controls on the gateway, a gateway in another project.
- **Area B in run 9 (repeat of run 8).** T30 and T32 passed again with the same setup, so each rests on two runs on one environment, by one operator. T31 passed in one attempt (one run). Its attribution to the gateway rests on one `gateway_requests` entry; T31R, meant to show the refusal is the registry's by changing only the registry, was INCONCLUSIVE because its fixture's model call got 404 on the regional host after registration (model not found there or no access), not the expected 200. A T31R re-test needs a model served on that host and a new pre-registration. The default setup (no token-binding opt-out) was not re-tested.
- **Script fault in T30-T32 `result.json` (runs 6 to 8).** The `expected` field holds the control text; the pre-registered expected text is in the first line of `output.txt` and in `command.txt`. Fixed before run 9 (results.md Findings 31).
- **T34 attribution.** The direct connection failed, but the runtime project had no firewall log entries at all. The agent's direct traffic likely never reaches the VPC (inference). T34 does not show that the firewall rule blocks it.
- **T29.** FAIL on the message prefix only, in both runs; the block itself worked. One prompt, one project, one region.
- **Organization-level tests in a test-only organization.** T36 and T38 changed organization-scope settings (a custom constraint and policy; an organization Model Armor floor), each applied by the human alone and removed or made non-enforcing the same day. The organization has no production workloads. Behavior in an organization with existing policies or workloads was not tested.
- **Model Armor floor settings remain after destroy.** With Google provider 8.8.0 a Terraform destroy of `google_model_armor_floorsetting` removes it from state only. The organization, folder and runtime-project floors still exist, non-enforcing, with their filter config unchanged. A later create updates them.
- **Roles and identities kept after the run.** Human decision 2026-10-28: the operator keeps the organization-level `roles/modelarmor.floorSettingsAdmin` and `roles/iam.denyAdmin`, and the T39b control service account (no keys) is kept for run-7. For run 7 the operator also got `roles/iam.accessPolicyAdmin` on the runtime project (IAP V2). These remain after run 7, pending a human decision. This departs from E4.5, which said the organization-level roles are removed at teardown. They remain a standing grant until the human removes them.
- **T39 and T39b scope.** One Terraform stack, one perimeter, one pipeline identity. The quota-project result is empirical; no Google documentation says how VPC-SC evaluates the quota project. The egress rule is specific to the two storage methods seen; a different provider version or resource set can need other methods.
- **T36 and T37 scope.** One custom constraint (bucket label) and one deny policy at folder scope, one exception each. Dry-run log arrival was seen once per run.
- **T33 and T34 scope.** One agent with a PSC interface, one proxy, one allowed host and one non-allowed host, one region.
- **Fixture and script faults in run 6.** Fixed with no verdict lost (aborted prechecks or infra faults): the gcloud model-armor endpoint, the T36 guard, the IAP extension metadata, exact-hostname registry entries, the Cloud Build staging bucket location, deny policy display name length, gateway one-operation limit. None changed an expected result. Details in [run-6.md](evidence/runs/run-6.md) and the Deviations in [results.md](results.md). Run 7 had no script faults and no retries; one infra fault (expired login before an apply, nothing created) and one held subnet in a reset ([run-7.md](evidence/runs/run-7.md)).
- **Run-order deviations.** Agent A started about 11 minutes before its wait ended; perimeter rules were applied with gcloud; stages were split. See [results.md](results.md), Deviations 9 to 21 (run 7: 17 to 21).
- **T12 tier.** The run-6 `result.json` tier reads Enforced; the report tier stays Configured (observed) because the test only reads policies.
- **Tool versions in runs 6, 7 and 8.** gcloud 590.0.1, Terraform 1.17.0, Google provider 8.8.0 (checked in a sample of five `result.json` files per run). Agent G in run 7: `google-cloud-aiplatform` 2.6.0, `google-adk` 2.13.0 (pinned; run 6 was unpinned).
